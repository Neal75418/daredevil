# 盤後資料定案與重抓設計（A 類：當日行情與籌碼）

> 狀態：設計待審（2026-09-26）
> 範圍：當日發布的全市場行情／籌碼資料「先抓到初值、之後不再更新」的問題，以及量測時順帶發現的上市估值日期錯位。
> 不含：營收、財報、董監持股、集保分散表的事後更正（B 類，另案）。

## 1. 問題

2026-09-26 資料稽核在 7 月中旬後發現一群錯誤，根因調查結論：

| 現象 | 根因 | 影響範圍（app DB） |
|:--|:--|:--|
| 上市成交量偏低 | 15:30 抓到的是**初值**（尚未計入鉅額交易，約 17:30–18:00 才補上）；當天已有「夠多列」，21:30 那輪就跳過不重抓 | 2026-07-16 起，1,744 列；9/24 抽查 21/21 筆差額＝當日鉅額交易量 |
| 法人買賣超（投信欄等）與官方現值不符 | 同上：T86 初值不含鉅額交易（例：7788 7/17 外資差 3,000,000 股＝鉅額） | 7/16–8/19，330 列；8/19 後 T86 在 15:30 還沒發布，改由 21:30 首抓，才碰巧正確 |
| 上櫃成交量口徑在 7/15 改變 | 歷史回補端點 `afterTrading/otc` 是「不含定價交易、整張」口徑（官方的 91–98%）；每日端點是官方口徑 | 2025-06-12～2026-07-14 共 266 天，另 2026-09-14 一天 |
| 上櫃成交量 7/15 後仍有零星偏低 | 同第一列：上櫃 15:30 也是初值 | 9/15–9/24 抽查 8 天：5／0／31／512／2／0／2／3 列不符 |

**共同根因**：價格與法人的每日同步以「當天已有超過 N 列」判斷完整並跳過，但「列數夠」不代表「數值已定案」。當沖、融資券、外資持股在每日流程裡本來就強制重抓（`UpdateService` 呼叫 `syncMarketWideData` 時硬寫 `force: true`），沒有這個問題；但它們在 15:30 大多尚未發布，當天實際只抓到一次（21:30）。

### 2.4 順帶發現：上市估值日期錯位

上市估值（本益比／淨值比／殖利率）用 OpenAPI `BWIBBU_ALL`。程式註解說「不回傳交易日」，所以用呼叫當天的日期標記；但回應其實**每列都有 `Date` 欄**，而 15:30／21:30 時它仍是前一交易日的資料。

逐日比對 52 個交易日（2026-07-15 起）：**35 天整批標成隔天**（該日值與官方前一日 100% 相同），17 天正確，沒有其他型態。

同類檢查（兩個 client 裡所有 `date ?? now` 標記處）：

- 上櫃估值、上櫃當沖讀回應裡的日期。
- 上市當沖比對回應日期與請求日期。
- 法人、融資券以回應日期寫入。
- 價格經稽核逐日比對收盤價，0 筆不符（若日期錯位，收盤會對不上）。

只有上市估值這一處有問題。

## 3. 目標與非目標

**目標**

1. 追蹤的資料集，同一天的資料會一直重抓，直到「隔天以後抓過一次」為止；不再用列數判斷完整。
2. 上櫃價格歷史改成官方口徑，與每日端點一致。
3. 上市估值用回應中的日期標記。
4. 修復既有錯誤資料，先在 DB 副本上彩排、經同意才動實際 DB。

**非目標**

- B 類（營收、財報、董監持股、集保）的事後更正。
- FinMind 來源的資料（上櫃逐檔外資持股、上櫃逐檔價格回補）：沒有免費的全市場歷史端點，另記風險不處理。
- 已產生的過去訊號（`daily_analysis`／`daily_reason`）不重算：保留當時實際看到的結果。
- 大盤指數、警示股：稽核數值全部一致，沒有初值問題。
- 上櫃當沖 8/21 前覆蓋率低（每日約 200 檔）：官方端點既然吃日期，可另案回補，本設計不處理。
- 研究用的 `tool/calibration.db`。

## 4. 設計

### 4.1 定案規則

> **一筆（資料集, 市場, 資料日）只有在「抓取時間的台北日期 > 資料日」時才算定案。**

**與先前討論版本的差異**：先前是「同日 20:00 以後抓的也算定案」。量測後改掉，原因：

- 上櫃價格沒有同日較晚時點的證據，9/18 還有一筆解釋不了的大量不符；20:00 這條線對上櫃沒有根據。
- 「隔天以後抓就一定對」有稽核全面佐證，不必依賴任何發布時刻。
- 代價只是每個資料日多抓一次歷史端點：追蹤 9 組（資料集×市場），每天約 9 次呼叫，都是免費官方端點。

21:30 那輪仍會重抓當天資料（因為還沒定案），所以當天晚上的訊號用的是較新的值。只是「定案」這個狀態要等到下一次有執行更新的交易日。

非交易日整輪更新會提早結束（`UpdateService` 步驟 1），所以週五的資料要到下週一 15:30 才會定案；連假同理。這是預期行為。

「台北日期」用 `TaiwanTime` 換算，時鐘可注入以便測試。注意 `DateContext.normalize` 是**裝置本地時間**的午夜，不是 UTC（`price_repository.dart` 的註解寫錯，順手改正）。

### 4.2 追蹤的資料集

`prices`、`institutional`、`dayTrading`、`margin`（兩市場）；`foreignShareholding`（僅上市）。共 9 組。

當沖、融資券、外資持股沒有「初值會變」的直接證據，仍納入。這次的錯誤正是「以為第一次抓到的就是定案值」，而且錯了好幾週都沒發現。納入的成本是每天 5 次免費呼叫，每組各自例外反而更容易出錯。

估值不納入：17 個標對日期的日子與官方 100% 相同，沒有數值會變的跡象；它的問題只是日期標錯（§4.8）。

### 4.3 狀態表

新增表 `market_day_fetch`：

| 欄位 | 型別 | 說明 |
|:--|:--|:--|
| `dataset` | TEXT | 上列 5 種之一 |
| `market` | TEXT | `TWSE`／`TPEx` |
| `date` | DateTime | 資料日，正規化方式與 `daily_price.date` 相同 |
| `fetched_at` | DateTime | 每日更新路徑：本輪更新開始時的台北牆鐘時間（`AppClock.now()`），比實際請求早——只會讓判定偏向未定案，不會把初值誤判成定案（例外見 §8：App 畫面與更新共用 client 快取的極低機率情境）。修復工具 `tool/refetch_market_days.dart`：工具啟動時的 `TaiwanTime.now()`，不是「本輪更新開始」——工具沒有「輪」的概念，一次執行就是一次 |
| `row_count` | INTEGER | 該次寫入的列數（診斷用） |

PK：`(dataset, market, date)`。

- **不存「是否定案」**：定案與否由 `fetched_at` 和 `date` 算出，避免旗標與事實不同步。
- **建表方式**：比照 `quarterly_report`／`pinned_thesis`，在開啟 DB 時用 `Migrator.createTable`（CREATE TABLE IF NOT EXISTS）補建。**不 bump schema fingerprint**，否則會清掉整個行情庫。`app_database.dart` 的 fingerprint 說明寫「新增 table 要 bump」，這裡照既有先例是例外，要在程式註解寫明。
- 不列入使用者資料白名單。將來若 fingerprint 重置，行情和這張表會一起清掉，之後回補（隔天才抓）自然都是定案，兩邊保持一致。

### 4.4 何時記錄一次抓取

**由發起全市場抓取的呼叫端決定是否傳入 ledger，實際記錄動作在 repository 裡**：repository 分不出「這次是不是全市場」——`tool/backfill.dart` 有幾條路徑只傳部分股票給同一個 repository 方法，所以由呼叫端決定要不要傳 `MarketDayFetchLedger`（部分股票的路徑不傳）；repository 在**寫入資料的同一個 transaction** 內呼叫 `ledger.report`，回報實際寫入的市場、資料日、列數——事實由源頭（repository）回報，不由呼叫端回推。

記錄的條件，全部成立才記：

1. **全市場抓取**。逐檔、部分股票的抓取不記（呼叫端不傳 ledger）。
2. **資料來自實際的網路回應**。實作上改成每輪更新開始時（`UpdateService._executeUpdate` 步驟 1 之後）清空 TWSE／TPEx 兩個 client 的記憶體快取（`clearCache()`），並以本輪開始時間作為整輪的 `fetched_at`——這樣不會有前一輪的快取被記成本輪抓取，常駐的 App 跨午夜時也不會把前一天快取的初值誤判成隔天抓的定案值。
3. **回應日期可驗證**（fail-closed，只改追蹤資料集的呼叫點，不改共用函式）：
   - **帶日期的請求**：回應日期必須等於請求日期，不符或沒有就整批丟棄。
     - 上櫃法人比照上櫃融資券現有的「傳哨兵日期」做法。
     - 上市 T86 比照上市當沖現有的字串比對。
     - `dailyQuotes`（§4.7）與上櫃當沖（§4.9）本來就是 fail-closed。
   - **不帶日期的請求**（每日價格、每日融資券，兩市場）：回應日期必須解析得出來，解析不出就整批丟棄，不能退回請求日期或今天。
     - **上櫃每日價格歸在這一類**。程式雖然有傳日期，但端點會忽略它，15:30 可能回前一日的資料。如果照「帶日期→必須相等」處理，前一日那份其實已定案的價格會被整批丟掉。
     - 可解析性已確認，不會誤丟正常的回應：上櫃每日回應的表格日期是 `115/07/08` 這種格式；上市 CSV 路徑固定產生 8 碼西元日期。
   - 不改共用函式的原因：上櫃 `extractTpexTable`（4 個呼叫點）沒帶日期時退回請求日期，上市 `TwParseUtils.parseAdDate`（6 個呼叫點）解析失敗時退回今天。直接改它們，會波及不在範圍內的端點。
4. **該市場的列數 ≥ 該組的記錄門檻**。不能用 `DataFreshness.fullMarketThreshold`（1500）：它是兩市場合計校準的，上市單邊只有約 1,200–1,300 列，會永遠記不進去。

**記錄門檻逐組訂定**。原則是「該市場在市股票數 × 比例」。現有各條回補的完整性判斷各不相同，無法共用一個函式：

| 資料集 | 現有回補的判斷 | 記錄門檻的比例 |
|:--|:--|:--|
| 價格 | `historicalMarketDayMinCoverageRatio` | 沿用 |
| 當沖（上市） | `twseBatchThreshold`（固定 100 列） | 新訂比例 |
| 當沖（上櫃） | 無現有回補（`tradingBackfillMinCoverageRatio` 在這裡是價格分母的覆蓋閘門，不是列數判斷） | 新訂比例，暫用 `tradingBackfillMinCoverageRatio` 的值 |
| 融資券 | `tradingBackfillMinCoverageRatio` | 沿用 |
| 外資持股 | `foreignShareholdingMinCoverageRatio` | 沿用 |
| 法人 | 兩市場合計 > 1500 | 新訂比例 |

實作計畫第一步先量最近 30 個交易日各組的實際列數，再定新訂比例的值，並確認沿用的比例在單一市場下站得住。

回補判定完整、但列數沒達到記錄門檻的日子，不會落入空窗：(b) 會把「追蹤起始日以後、沒有定案狀態」的日子都列為候選，包括完全沒有狀態列的日子。

狀態列的 `date` 一律用**實際寫入的資料日**。例：9/24 15:30 那輪上市融資券不帶日期請求，拿到的是 9/23 的資料並寫在 9/23（日誌 `[TWSE] 融資融券: 1297 筆 (2026-09-23)`）。這時該記 `(margin, TWSE, 9/23)`，而且因為是隔天抓的，記下去就是定案。價格要用 `processDailyPrices` 回傳的分市場資料日。

**寫入規則**：資料與狀態在同一個 transaction 寫入；同一鍵以最後寫入者為準（last-writer-wins），不取較大的時間。App 與 launchd 同時跑時，較晚寫入的若是初值，只會被重新判為未定案，不會把初值誤標成定案。

### 4.5 同步流程的改動

**(a) 當日路徑：只有價格和法人要改**

| 位置 | 現行略過條件 | 改成 |
|:--|:--|:--|
| `PriceRepository.syncAllPricesForDate` | `getPriceCountForDate > fullMarketThreshold` | 兩市場都已定案才跳過 |
| `InstitutionalSyncer` 當日判斷（`_isComplete`） | `isDayComplete` | 兩市場都已定案才跳過 |
| `InstitutionalRepository` 內部 | `getInstitutionalCountForDate > fullMarketThreshold`（syncer 傳 `force: false` 時生效） | syncer 決定要抓時傳 `force: true`，讓這道閘不再二次攔截 |

當天的資料在當天不可能定案，所以交易日當天這兩條實際上**每次都抓**。定案判斷只在「對過去日期呼叫、且沒帶 `force`」時才會真的跳過。例如盤前執行時目標日回滾到上一個交易日，而那天已經定案。

`_isComplete` 同時給當日和回補用。改的是當日那個呼叫點，回補那個維持原本的完整性判斷（見 (c)）。

當沖、融資券、外資持股的 repository 閘門，在每日流程中已被 `force: true` 繞過，**不改**。它們只需要補上狀態記錄。

實作計畫要用 grep 全面列舉一次，確認沒有漏掉的閘門。

**(b) 重抓未定案日**（新增，每輪在當日路徑與既有回補之後、評分之前執行）

對每組（資料集, 市場）：

1. **候選日**：同時符合以下條件的交易日。
   - 資料日 **早於台北今天**。當天的資料交給 (a)，避免同一輪用歷史端點再抓一次今天。
   - 在回補窗內：沿用 `ApiConfig.tradingBackfillLookbackDays` 的 40 個**日曆天**（約 27 個交易日）。
   - 不早於**追蹤起始日** `finality_tracking_since`。
   - 沒有定案的狀態列：可能是有列但未定案，也可能完全沒列（追蹤開始後從沒成功記錄過）。
2. 依 §2.2 的歷史端點逐日重抓、覆寫、記錄狀態。
3. **順序**：價格先抓，當沖再抓，因為當沖比例的分母是成交量。
4. 每組每輪最多 `M` = 10 天，避免長時間關機後一次打太多；剩下的留給下一輪。`M` 放在 `ApiConfig`，與既有回補上限並列。
5. 法人一次請求同時拿兩個市場：任一市場未定案，就兩市場一起重抓，計入兩組各自的 `M`。

**追蹤起始日**：第一次執行更新時，在 `app_settings` 寫入當天的台北日期，之後不再變動。寫入要用「不存在才寫」（`InsertMode.insertOrIgnore`），不能用現有會覆寫的 `setSetting`，以免 App 和 launchd 同時首次執行時互相覆蓋。現有 DAO 沒有這種寫法，要新增一個方法。寫入時機放在 (b) 的入口。**「非交易日整輪會提早結束，所以起始日一定是交易日」只對 CLI／WorkManager 成立**——兩者都走 `runHeadlessUpdate`（`lib/app/headless_update_runner.dart`），在建服務圖之前就以真實現在時間判斷非交易日並整輪跳過。GUI（`today_provider.dart` 直呼 `UpdateService.runDailyUpdate()`，不經 `runHeadlessUpdate`）週末仍會執行：`_executeUpdate` 把這一輪要用的 `targetDate` 回溯到上一交易日，**驅動整輪當日同步**（不只是評分），但 (b) 的 `today` 參數仍是 `_clock.now()` 的真實現在時間，所以起始日**可能是週六**這類非交易日。

影響很小，理由有二：一是候選日不受影響——`refetchCandidateDays` 只把 `since` 當下界（`from = max(since, windowStart)`），候選日另外過濾 `TaiwanCalendar.isTradingDay`；`since` 落在週六或落在下一個交易日（例如下週一），兩者之間沒有其他交易日，篩出的候選日集合完全相同。二是即使起始日本身非交易日也不影響定案判斷——GUI 那一輪的 `ctx.ledger.fetchedAt` 是 `_clock.now()`（週六，真實現在時間），而回溯後那一輪當日同步實際寫入的資料日是上一交易日（週五）；週六 > 週五，依 §4.1 定案規則，週五的資料在**同一輪**就會被記為定案——這本來就是預期行為（該資料確實是隔天才抓的），不是起始日非交易日造成的副作用。兩條路徑都透過 `AppDatabase` 讀寫 `app_settings`，CLI 不需要 Riverpod。

- `app_settings` 在使用者資料白名單內，fingerprint 重置時不會被清掉。
- 不能用「狀態表最早的資料日」代替。上線第一輪，(c) 的回補路徑就可能替很舊的缺漏日寫下狀態（價格 Phase 0 的窗口是 `historyRequiredDays`，遠超 40 天）。起始日因此被拉回過去，窗內所有舊日子都會變成候選，在未經彩排的情況下自動改寫舊資料。
- 固定起始日讓這個機制上線即生效，又不會回頭去碰舊資料。舊資料交給 §5 的一次性修復；修復工具不讀、也不改這個起始日。

日曆漏標的休市日（例如颱風停市）會回 0 列、不記狀態，每輪都會重試，直到滑出窗外。這種日子有 `M` 上限、窗口也有限，代價有界。日曆本身有年度核對工具。滑出窗外仍未定案的日子只記 warning（筆數與前 10 筆），不進 errors——它們不會自己消失，進 errors 會讓之後每一輪 launchd 都回報失敗；需要用 §5 的修復工具處理。

**(c) 既有回補路徑**：略過邏輯不動，**成功寫入後依 §4.4 記錄狀態**。這些路徑包括價格 Phase 0、法人回補、當沖／融資券 40 天缺漏回補、外資持股回補。它們多半是隔天以後才抓，記下去就是定案。

上櫃當沖加入 40 天缺漏回補（§4.9）時，要用上櫃自己的價格覆蓋閘門與獨立的斷路器來源。現行閘門是照上市設計的。

**覆寫語意**：以 `insertOrReplace` 寫入，**不刪除任何列**。

對法人要多處理一件事：現行寫入會濾掉全 0 的列，而評分端把「沒有列」當成 0（`BatchDataBuilder` 的無進出補零）。如果某股初值非 0、定案值全 0，初值就會留著。

解法：維持「不寫全 0 列」的不變量（DB 目前三法人全 0 的列是 0 筆）。重抓時，對**回應中明確出現、但三法人淨額全為 0** 的代號，刪除該（代號, 日）的舊列。

不採「寫入全 0 列」的原因：讀取端把「有沒有列」當成訊號，多出全 0 列會改變數字。

- 籌碼異常偵測的法人爆量：以近 30 列的 `AVG(ABS(total_net))` 當基準，並要求 `COUNT(*) >= 10`。
- 法人排行的連買／連賣天數：遇到 0 就中斷。
- `BatchDataBuilder.fillNoActivityDays`：窗內完全沒有法人列時判定為「沒資料」。
- 列數判斷 `getInstitutionalCountForDate`／`isDayComplete`。

這條規則在實際資料中會觸發。官方回應會列出「有交易、但三法人淨額全為 0」的股票：2026-09-24 上市 T86 有 25 列、上櫃有 30 列（例如自營商避險買賣量相等）。

- 「全 0」的判定沿用現行過濾條件（`totalNet`、`foreignNet`、`investmentTrustNet` 皆為 0）。
- 刪除依據是**過濾前**的回應代號清單；`syncAllMarketInstitutional` 在過濾之前就拿得到這份清單。
- 另一種情況「初值有列、定案完全不發列」幾乎不會發生：鉅額交易只會讓買賣量變大，初值有列的股票，定案時一定也有列。
- 實作計畫第一步要驗證：存下 7/17 這類鉅額交易日的原始回應，比對初值與定案值，確認上面的推論。

不採「刪除回應裡沒有的列」的原因：

- `daily_institutional` 沒有市場欄，要靠 `stock_master.market` 反查。轉市場股票的舊列會被歸錯市場，然後誤刪。
- 寫入前會用在市股票清單過濾，已下市股票永遠不在新結果裡，修復時它們的列會被刪。
- 法人兩市場並行抓取，一邊失敗時回空清單；若照樣刪除，那個市場當天會整批清空。

### 4.6 衍生值：當沖比例

`day_trading.day_trading_ratio` = 當沖成交股數 ÷ 當日成交量 × 100，並夾限在 `[0, dayTradingMaxValidRatio]`。成交量被更正後，比例也要跟著重算。

- 把比例計算抽成一個純函式，當沖寫入與重算共用。
- **任何路徑**寫入全市場價格後，都用 DB 內既有的 `trade_volume`，對「這次寫入價格的代號 × 該日」重算比例。包括當日路徑、(b) 重抓、價格 Phase 0 回補（掛在它每個（日, 市場）寫入成功之後，每輪最多 30 次）、§5 修復工具。純 DB 操作，不打 API。
  - 範圍用「代號」而不是「市場」，因為 `day_trading` 沒有市場欄，用市場反查會重演轉市場股票被歸錯的問題。
  - 分母取法沿用現行當沖寫入的邏輯，包括同日時間戳變體的範圍查詢備援。分母（當日成交量）缺失或為 0 時**保留原比例**，不改寫成 0，以免回應裡沒有的代號被洗掉。
- 當沖的狀態記錄多一個條件：該（市場, 日）的價格覆蓋要達到門檻（比照 `MarketDataUpdater` 現有的上市當沖回補閘門）。上市當沖寫入時沒有這道閘門，分母取不到就寫 0；不加這個條件的話，價格缺漏的日子（例如 fingerprint 重置後）會把整片 0 記成定案。
- (b) 先抓價格再抓當沖，同一輪的當沖重抓會直接用到新成交量；上面的重算涵蓋其餘情況（只重抓價格、Phase 0 事後補上價格）。
- `tool/backfill_tpex_day_trading.dart` 另有一份公式，而且語意不同：沒有價格時工具不寫那列，repository 則寫 0。共用函式要保留兩種呼叫端各自的缺價處理；工具去留另案，但公式要改用共用函式。

### 4.7 上櫃價格來源統一

- `TpexClient.getAllDailyPricesHistorical` 改打 `dailyQuotes`。它的列格式與每日端點相同（成交股數在 index 8），**只共用逐列解析** `_parseDailyPriceRow`，包括欄數下限與 `isTpexPriceCode` 過濾。
- 表格外層不走 `extractTpexTable`，因為它在回應沒帶日期時會退回請求日期。保留 `parseAfterTradingOtcDailyPrices` 現有的頂層日期守衛：回應日期不符就整批丟棄。
- `afterTrading/otc` 不再使用。
- 每日路徑維持 `daily_close_quotes`：口徑已驗證一致，換端點沒有好處，還會多一個「15:30 當天是否已發布」的未知數。

### 4.8 上市估值日期

`TwseClient.getAllStockValuation` 改讀每列的 `Date`（民國 `YYYMMDD`）：

- 整批應只有一個日期。出現多個日期、缺欄位或解析失敗，就整批丟棄並記 warning。寫錯日期比沒資料糟，這與上櫃當沖的既有原則一致。
- 呼叫端傳入的 `date` 不再當標記用。15:30 拿到前一日的資料就寫回前一日，覆寫同值，無害。當天的估值要等 OpenAPI 更新後的下一輪才會出現。
- 唯一呼叫端 `FundamentalRepository` 本來就逐列讀 `date`，不受影響。`fundamental_repository.dart` 裡「BWIBBU_d」的註解是錯的，順手改正。`parseValuationRows` 改簽章會影響既有測試 `twse_valuation_null_test.dart`，要一起改。
- 下游讀的是「評分日以前最新一筆估值」（`getLatestValuationsBatch(asOf:)`），估值規則的新鮮度門檻是 7 天（`FundamentalParams.valuationMaxStaleDays`）。晚一天不會被擋，改完只是如實反映「今天的估值還沒公布」。
- 修復要用的歷史端點 `BWIBBU_d?date=` 目前沒有 client 方法，要新增方法與 parser（§5）。

### 4.9 上櫃當沖帶日期

`TpexClient` 取上櫃當沖時帶 `date`，並比照上市改用「回應日期 ≠ 請求日期就丟棄」的守衛。現行「未來日期／過期太久就丟棄」的守衛，是為了補「無法比對請求日期」的缺口，改完後由等值比對取代。快取 key 要含日期（現在是常數 `'tpexDayTrading'`，帶日期後會回錯天）。

以下「端點不給歷史」的說法要一起修正：

- `MarketDataUpdater` 的警告改成直接用官方端點補缺漏日。
- `tool/backfill_tpex_day_trading.dart` 檔頭（工具本身另案決定去留）。
- `day_trading_dao.dart`、`trading_repository.dart`、`tpex_client.dart`、`market_data_updater.dart` 裡的同類註解。實作計畫要 grep 全部列出。

## 5. 既有資料修復（一次性）

新增 CLI `tool/refetch_market_days.dart`。重抓邏輯直接呼叫 §4.5(b) 的同一個函式，不另寫一套。`--from`／`--to` 範圍內的交易日**不論狀態一律重抓**，不受 `M`、40 天窗與追蹤起始日限制。

```
dart run tool/refetch_market_days.dart --dataset prices --market TPEx --from 2025-06-10 --to 2026-09-24 [--db <path>] [--dry-run]
```

| 範圍 | 原因 | 約略呼叫數 |
|:--|:--|--:|
| 上櫃價格：DB 中全部交易日（2025-06-10 起） | 口徑（266 天＋9/14）；7/15 後的初值 | ~320 |
| 上市價格：2026-07-16 起 | 鉅額交易初值 | ~50 |
| 法人兩市場：2026-07-16～2026-08-19 | 鉅額交易初值 | ~50 |
| 當沖比例：隨上面兩列價格重算（§4.6） | 分母更正 | 0（純 DB） |
| 上市估值：2026-07-15 起全部 | 日期錯位。用新增的 `BWIBBU_d` client 逐日重抓；估值不在 (b) 的追蹤範圍，工具要有獨立的估值分支 | ~52 |

**驗收標準**：上列範圍內、`stock_master` 裡的股票，與官方不符列數歸零。已下市、不在 `stock_master` 的股票不會被覆寫，不列入驗收。範圍外不得有任何變動。

**參數與行為**：

- `--to` 一旦落在台北今天或更晚一律拒絕（當天資料還沒定案，統計出來的「成功/失敗」筆數沒有意義）。
- 退出碼：`0` 全部成功；`1` 有失敗日或未預期例外；`2` 參數錯誤或 DB 不可用；`4` 限流中止。
- **續跑提示**：部分失敗時（網路錯誤停掉某組剩餘天數，或被限流中止），工具印出「總交易日數、已嘗試幾日、未嘗試幾日」，並直接標出下次要用的 `--to`（由 `MarketDayRefetcher` 回報的 `stoppedAt` 反推，不靠嘗試次數回推——次數在中止發生於候選範圍內最舊那一天時會失準）。

**執行程序**（依專案規則：實際 DB 唯讀檢查，任何寫入要先彩排、經同意）：

1. 對 DB 快照（`VACUUM INTO` 副本）跑 `--db <副本>`。
2. 用稽核腳本比對副本與官方，並對修前修後逐表 diff，確認符合驗收標準。
3. 把彩排結果交給使用者，同意後才對實際 DB 跑；跑之前先備份實際 DB（`VACUUM INTO` 一份副本＋`PRAGMA integrity_check` 驗證備份可還原）。避開 15:30／21:30 launchd 排程時段。
4. 跑完再用稽核腳本驗一次實際 DB。

## 6. 錯誤處理與可見性

- 單一（資料集, 市場, 日）重抓失敗：不寫狀態，下輪再試。錯誤照現行 syncer 慣例進更新摘要的 errors。
- **`NetworkException`**（單日 4xx／逾時等）：只停該次 attempt 涵蓋的組別之後的天數，**其他組別照常執行**——單一（資料集, 市場, 日）的網路錯誤不代表整輪都會失敗，下一輪自然再試。**法人是例外**：兩市場共用同一個 day-loop（任一市場未定案就兩市場一起抓），`break` 會讓兩個法人組別一起停，不是各自獨立繼續。
- **`RateLimitException`**：中止整輪剩下的重抓（所有組別），已完成的保留；沿用 `rateLimitedAbort`。網路錯誤範圍侷限（單一請求失敗），限流是全域資源耗盡，因此後者要整輪中止、前者不用。
- 每輪日誌輸出一行摘要：各組重抓幾天、成功幾天、剩幾天未定案。
- 未定案且已超出回補窗的日子：日誌 warning，列出（資料集, 市場, 日）。這種情況代表那筆資料會永遠停在初值。

## 7. 測試策略

- **定案判定**（純函式）：台北時間跨日邊界（資料日 23:59 抓 vs 隔日 00:00 抓）、裝置時區不是台北時的換算。
- **當日路徑**：已定案就不打 API；未定案時即使列數遠超門檻也要打 API。價格與法人各一條，這是本次 bug 的回歸測試，必須在修改前先紅。法人要涵蓋 repository 內那道閘不再二次攔截。
- **記錄條件**（§4.4）：追蹤抓取不走快取、部分股票不記、回應日期不符整批丟棄且不記、逐組門檻（上市單邊約 1,200 列要能記進去）。非追蹤端點的日期退回行為不變。
- **重抓 (b)**：只挑早於今天的候選日、追蹤起始日以前不挑（即使 (c) 替更舊的日子寫了狀態）、40 日曆天窗與每輪上限 `M` 截斷、價格先於當沖、法人任一市場未定案即兩市場一起抓、回 0 列不寫狀態、限流中止保留已完成。
- **追蹤起始日**：第一次執行時寫入、之後不變（已存在時不覆寫）；修復工具不改它。
- **法人覆寫**：初值非 0、定案回應全 0 的股票（fixture 取自實際回應中的全 0 列），重抓後該（代號, 日）列被刪除；DB 不會出現全 0 列；回應裡沒有的代號（含轉市場、已下市）舊列不動；單邊失敗時另一市場照常寫入，失敗那邊不記狀態。
- **當沖記錄閘門**：價格覆蓋不足的（市場, 日）即使當沖列數夠也不記狀態；Phase 0 補上價格後比例會被重算。
- **日期守衛**：帶日期請求時回應日期不符就丟棄；不帶日期請求時回應日期解析不出就丟棄；非追蹤端點行為不變。
- **並行**：較晚寫入的初值會讓該列回到未定案。
- **當沖比例重算**：成交量變了比例跟著變；夾限與寫入路徑一致（共用函式）；分母缺失時保留原比例。
- **上櫃歷史解析**：`dailyQuotes` fixture（取自實際回應）、回應日期不符時整批丟棄。
- **上市估值日期**：單一日期正常、多日期整批丟棄、缺 `Date` 整批丟棄、民國年解析。
- **上櫃當沖**：請求日期與回應日期不符時整批丟棄；快取 key 含日期。
- **建表**：既有 DB 開啟後補建、既有資料零損失。寫法參考 `watchlist_groups_default_column_migration_test.dart`。
- **狀態記錄覆蓋率**：每條全市場寫入路徑成功後都有狀態列。實作計畫列出所有路徑後逐一測。

| FinMind 來源資料可能也有初值問題 | 非本設計範圍，記錄為已知風險 |
| App 的畫面與更新共用同一個 client | 若某個請求在本輪開始**之前**發出、清快取**之後**才回來，舊回應會被寫進快取，本輪再讀到就會以本輪開始時間記錄。要發生必須剛好有一個跨越午夜、又跨越更新開始的在途請求，機率極低；若要消除，可給 client 快取加世代號（清快取時遞增、寫入前比對） |

## 9. 考慮過但不採用

- **launchd 改到 18:00 以後才跑**：訊號延後，而且 App 手動更新和手機背景更新仍會在早上抓到初值，治標。
- **每輪固定重抓前一交易日、不記狀態**：Mac 關機跨過那一天時，那天就永遠停在初值。
- **同日 20:00 以後即定案**：見 §4.1，上櫃沒有證據。
- **由 repository 自行判斷是否全市場並記錄**：分不出來，改由呼叫端傳入 ledger 決定（見 §4.4）。
