# 除權息漲跌修正 — 設計

> **狀態（2026-10-27）**：第二版，待審查。第一版（2026-10-07，全文見 `c4263411`）的核心公式「漲跌＝收盤 − 除權息參考價」被
> 審查推翻（見文末「第一版審查紀錄」）；本版改用交易所公告的平盤價，來源由 2026-10-27 spike 實測（見「平盤價來源」）。
> 大盤熱力圖（`2026-10-07-market-heatmap-design.md`）依賴本項，它第 1 節的兩條需求本版全部採納（見「熱力圖需求的對照」）。

## 背景

交易所的漲跌＝收盤 − 當天的平盤價（開盤競價基準）。平常日子平盤價等於前一天收盤；除權息、減資或面額變更恢復買賣、新股首日、
前一天沒成交等日子則不等於。

現況是這些「不比價」的日子，`daily_price.price_change` 上市存 0、上櫃存空值（見「量測」）。使用者看到的是：
- 該檔該日顯示 0%；
- 或者因為存空值，讀取端退回前一筆收盤，把股息算成跌幅（例：2947 2026-10-07 顯示 −3.35%）。

讀取端幾乎都用「收盤 − 漲跌價差」回推昨收（`PriceCalculator.calculatePriceChange`、`LiveQuoteMerge`、大盤統計）。所以只要
`price_change` 存對，下游自動正確。

## 目標與成功標準

- `daily_price.price_change`＝收盤 − 交易所當天的平盤價。平盤價不明時為空值，不得為 0。兩個市場、每一條寫入路徑都成立。
- 已經正確的值被之後任何一次寫入覆寫，只能變成正確值或空值；有平盤價的列（含每一列除權息）一定保持正確。
- 既有資料用修復工具修一次：
  - 上市不比價日的 0 → 正確值；
  - 上櫃除權息日的空值 → 正確值。
- 大盤家數照官方口徑，排除除權息日的列；產業平均照算（2026-10-07 使用者決定）。
- 漲跌幅提醒與族群排行「今日」改用漲跌價差。
- 平常每輪多 1～2 個請求。

## 非目標

- **盤中即時報價不改**：MIS 的 `y` 已經是平盤價（見「平盤價來源」）。
- **族群排行 5 日、20 日與其他多日報酬**：用前後收盤算，除權息缺口會被算成跌幅；要改用還原股價，另案處理。
- **評分規則與候選排序**：以下規則用單日前後收盤算漲跌，除權息日會把股息當成下跌：`pullback_rules.dart` 的跌停判定、
  `volume_rules.dart`、`fundamental_rules.dart`、`fundamental_technical_filter.dart`。每日候選排序（`price_candidate_filter.dart`）
  用的是來源原始的漲跌，不是存下來的 `price_change`。這些都是既有行為，本項不改；「下游自動正確」只指讀 `price_change` 的地方。
- **每日第一次寫入的來源不換**：仍用 `STOCK_DAY_ALL`。
- **大盤統計混入 ETF**：既有差異，官方「股票」類不含 ETF，本項不改。

**寫入**：
- 新增或覆寫價格列只經 `insertPrices`（批次 insert-or-replace）。呼叫點有 `price_repository.dart` 4 處、`tool/backfill.dart` 1 處。
- 整個市場某一天的寫入只有三個函式：
  - `syncAllPricesForDate`：每日寫入。
  - `backfillTwsePricesByDate`、`backfillTpexPricesByDate`：呼叫者是 `MarketDayRefetcher`（步驟 5.5 與 `tool/refetch_market_days.dart`）、
    `HistoricalPriceSyncer` 的 Phase 0、`tool/backfill.dart`。
- 另有兩個維護動作不碰漲跌欄：啟動時把收盤 0 清成空值、刪除無效代號。

**定案**：
- 寫入後由 `_afterMarketDayWrite` 重算當沖比例，並向 ledger 回報市場、資料日與列數。
- 定案＝抓取日晚於資料日。步驟 5.5 只重抓沒定案的日子：追蹤起始日以後、40 天窗內，每組每輪最多 10 天；滑出窗仍未定案的只記 warning。

**讀取**：
- `PriceCalculator.calculatePriceChange`：漲跌價差優先；空值時退回前一筆收盤。
- `LiveQuoteMerge`：正式資料的昨收＝收盤 − 漲跌價差；空值時呼叫端退回前一交易日收盤。
- `market_overview_dao.dart` 用 `price_change` 的家數類查詢有 4 個：
  - 漲跌家數；
  - 漲跌家數歷史（含上漲、下跌成交值）；
  - 漲跌停家數；
  - 產業表現（平均漲跌幅、各產業漲跌家數；檔數門檻以 `HAVING COUNT(*)` 套在全部列上）。
- 漲跌幅提醒 `UpdateService._fetchAlertPrices`：用前後收盤算。
- 族群排行「今日」（`IndustryRankingService`，`RankingWindow.d1`）：`PriceCalculator.ret1d`，也是前後收盤。
- 盤中提醒：`IntradayQuote.changePercent` 以 MIS 的昨收（`y`）計，已經是平盤價。

**官方口徑**：證交所漲跌家數另列「無比價」，不算漲、跌、平。2026-10-07「股票」類：上漲 588、下跌 387、持平 99、未成交 5、無比價 3。

## 設計

### 1. 資料表

`daily_price` 加一欄 `base_price REAL NULL`：交易所當天的平盤價。
- 只存來源直接給的值（上市 TWT84U、上櫃 exDailyQ），不從漲跌回推；沒取得為空。
- 既有 DB 照 `_ensureDividendPriceColumns` 的先例，在 `beforeOpen` 用 `ALTER TABLE ADD COLUMN` 補欄。fingerprint 是手動維護的常數，
  不 bump，所以不會觸發重置。Drift 表定義同步加欄、重產 `*.drift.dart`。

**取捨**：另開一張「平盤價表」也可行，但有兩個缺點：
- 體積大：上市每檔每天一列，連主鍵索引估計每年 30 MB 以上；放在欄位每年約 3～4 MB（約 35 萬個值 × 8～9 位元組）。
- 要另外處理順序：平盤價和價格分開兩張表，就要處理「平盤價先到、價格列還沒寫」的情況；放在同一列沒有這個問題。

### 2. 寫入規則（`insertPrices`，唯一入口）

由 insert-or-replace 改成依 `(symbol, date)` 的 upsert。每一筆：

- **開高低收、成交量**：用新值，跟現在一樣。
- **`base_price`**：新寫入有帶就用新的，否則保留舊的。
- **`price_change`**，依序判斷：
  0. 新收盤是空值（沒成交）→ 空值，不論來源給什麼。現在上市有 873 列沒成交卻存 0（副本，跨 279 天；例：3432 2026-09-15），
     上櫃沒成交的列本來就是空值。四個家數查詢都要求收盤非空，不受影響。
  1. 合併後的平盤價有值 → 收盤 − 平盤價，四捨五入到小數 2 位（價格最小跳動 0.01）。
  2. 否則，如果新寫入有帶漲跌欄（含明確的空值，例如 `X0.00`、上櫃的除息文字）→ 用新值。上市 `STOCK_DAY_ALL` 的「需要平盤價的列」
     沒有平盤價時，寫入前已改成空值（第 3 節）。
  3. 否則（FinMind 這類根本沒有漲跌欄的寫入）→ 收盤沒變就保留舊的漲跌，收盤變了就存空值。

  第 2、3 條要分開，是因為 STOCK_DAY 明確說「這天不比價」時要寫空值。如果用第 3 條保留舊值，2025-06 以來存錯的 0 會被留下來。
  SQL 的 `excluded` 分不出「沒帶」和「帶空值」，實作要依 companion 的 `priceChange.present` 走兩種 upsert。
- **沒有舊列時（insert 分支）同樣套這些規則**：SQLite 的 `ON CONFLICT DO UPDATE` 只在衝突時生效，15:30 的第一次寫入走的是 insert
  分支。規則只寫在 DoUpdate 裡的話，有平盤價時仍會把 `STOCK_DAY_ALL` 給的 0 寫進去。所以插入值由 Dart 先依第 0、1、2 條算好
  （沒有舊列，合併後的平盤價就是新值）。
- **寫 `price_change` 的地方只有兩處**：`insertPrices`，以及第 4 節的 `applyBasePrices`。由結構測試掃 `lib/` 與 `tool/` 守住
  （放行兩個不碰漲跌的維護動作）。

### 3. 整個市場某一天的寫入：同一天的平盤價一起寫

三個函式（`syncAllPricesForDate`、`backfillTwsePricesByDate`、`backfillTpexPricesByDate`）都一樣：先抓價格，再抓同一天的平盤價，
最後把兩者寫進同一個 transaction。網路請求都在 transaction 外。

**上市**：
- 價格抓到、而且不是空的，才以價格的資料日抓 TWT84U。回應要 `stat` 是 OK、`date` 等於資料日、`total` 等於實際列數，否則視為
  沒抓到。抓到時每一列帶上 `base_price`。
  - 每日路徑以 `STOCK_DAY_ALL` 回應的資料日為準。15:30 端點若還是前一天的資料，就抓前一天的平盤價。
- MI_INDEX 的 `X` 解析成空值；`+`、`-`、空白照舊。

**上櫃**：
- 解析器把漲跌欄是文字的列標成不比價。文字指不是數字，也不是 `---`、`--`、空白。
- 這一批有不比價列時，才抓 exDailyQ 單日，把「開始交易基準價」帶給清單上的列。沒有就不抓：10 月到隔年 5 月多半不用抓。
  - 兩個端點都實測過：歷史端點 dailyQuotes（Task 15 下載的 10 天）與每日端點 daily_close_quotes（2026-10-27 15:05 抓）。10/27 的
    00888、00958B 寫「除息」，3691 寫「除權」，一般股票是數字（例：6488 −12.00）。00958B 代號帶字母，會被 `isTpexPriceCode`
    濾掉、不寫入；照本設計，寫入的兩檔會是 00888 −0.32、3691 +10.5（32.12 − 32.44、119.50 − 109.00）。
- `ExRightResult` 新增的這一欄解析失敗時存空值、不拒收整批，不影響 `DividendSyncer`。

**需要平盤價的列**：收盤非空，而且來源的漲跌分不出是不是不比價的列。
- 範圍：上市 `STOCK_DAY_ALL` 漲跌是 0 的列、上市 MI_INDEX 標 `X` 的列、上櫃有文字標記的列。
- 以實際寫入的列為準，也就是 `targetSymbols` 過濾之後。
- 漲跌是非 0 數字的列，來源的漲跌就是官方值，不需要平盤價。
- 上市 `STOCK_DAY_ALL` 的這些列沒有平盤價時，漲跌在寫入前改成空值：分不出不比價和真的平盤，需求 2 不准暫存 0。

**寫入後判斷要不要回報定案**（同一個 transaction 內）：upsert 完，查這批「需要平盤價的列」合併後還有幾列沒有平盤價，記為 N。
每個市場的平盤價狀態由兩部分組成：**抓取結果**與 **N**。

| 抓取結果 | 意思 | N＝0 | N＞0 |
|:--|:--|:--|:--|
| `fetched` | 回應可信 | 回報定案 | 回報定案、記 warning（清單不全）；兩個例外見下方 |
| `failed` | 網路錯誤、回應不可信（`stat`、`date`、`total` 不符）、解析失敗 | 回報定案、只記 log | **不回報定案** |
| `rateLimited` | 限流（帶原始例外） | 回報定案 | **不回報定案** |
| `notNeeded` | 上櫃這批沒有文字標記，沒抓 | 回報定案 | （不會發生） |
| `skipped` | 價格回空，或 `withBasePrices: false`，沒抓 | 照現在的行為 | 照現在的行為 |

- **N＝0、但這次沒抓到**也照常回報：先前的寫入已經存好平盤價（例：15:30 抓到了、21:30 重寫時 TWT84U 失敗），或這天根本沒有需要的列。
- **抓取失敗或限流、而且 N＞0** 才不回報：當沖比例照算，這一天不會被記成定案，交給步驟 5.5 依既有規則重抓（40 天窗內、每組每輪最多
  10 天，滑出窗記 warning）。不能照常回報的原因：隔天的定案重抓那一次如果剛好抓不到，那一天就會被記成定案，之後不再重抓，空值就永久留下。
- **抓到了、但清單上沒有某檔需要的列**：照常回報定案，記 warning。
  - 這只會是來源前後不一致：9/16 MI_INDEX 有效代號的上市列 1,229 列，0 列不在清單上。
  - 重抓也拿不到同一份清單的缺口。不回報的話，那天會讓步驟 5.5 連續 40 天每輪記 errors。專案的原則是「不會自己消失的，不進 errors」
    （`update_service.dart` 步驟 5.5 的註解）。
  - 上市的缺口由下面的摘要計數持續可見。上櫃只在寫入當下的 warning 看得到：上櫃的計數靠配發表，配發表的上櫃列也來自 exDailyQ，
    exDailyQ 沒列的那檔，配發表多半也沒有。
  - **例外一：上櫃一列都對不上（含 exDailyQ 回空清單）→ 算 `failed`**。有文字標記卻完全對不上，比較可能是 exDailyQ 還沒更新，
    重抓有機會拿到。
  - **例外二：缺口來自上市 `STOCK_DAY_ALL` → 一律不回報**，交給隔天的 MI_INDEX 重抓判斷。這些列可能是真的平盤股，MI_INDEX 的方向欄
    空白會把它寫回 0（不需要平盤價），重抓一次就恢復。X 列缺清單時，才在 MI_INDEX 那一次照「`fetched` 而 N＞0」記定案。

**平盤價的錯誤放進回傳值，不往上拋**：
- 三個函式在回傳值裡帶每個市場的平盤價狀態（抓取結果＋N）。
- 平盤價這一段的任何錯誤都不拋：平盤價在 transaction 之前抓，價格已抓到、要和平盤價寫進同一個 transaction，在這裡拋出價格也寫不進去、
  呼叫端也拿不到回傳值。例：每日路徑的資料日校正、候選股、
  `pricesUpdated` 都在回傳之後才處理。
- 價格本身的抓取照舊 rethrow `RateLimitException`、`NetworkException`。
- 這是 CLAUDE.md「錯誤處理」的新例外。先例是 `HistoricalPriceSyncResult.rateLimitError`：已抓到的資料要保留時，把限流放進結果、
  不 rethrow。實作時同步寫進 CLAUDE.md 與 `.claude/rules/update-pipeline.md`。

**呼叫端怎麼處理**：

下表的「缺」指不回報定案的情況：`failed` 而 N＞0，以及上面兩個例外。`fetched` 而 N＞0（不含例外）只記 warning；`failed` 而 N＝0
只記 log。

| 呼叫端 | 缺 | `rateLimited`（不論 N） |
|:--|:--|:--|
| `_syncDailyPrices`（每日） | 照常處理回傳值後 `recordError`（哪個市場、N 列漲跌暫存空值）→ 本輪 PARTIAL | 照常處理回傳值後設 `rateLimitedAbort`、`recordError`，寫法同價格限流 |
| `MarketDayRefetcher.attempt`（步驟 5.5、`tool/refetch_market_days.dart`） | 記進 `summary.errors`（步驟 5.5 會轉成本輪 errors；修復工具 errors 不為空時 exit 1）；這一天沒定案，下一輪再抓 | 先照常計算這一天的定案（N＝0 時這天已記定案、算進 `summary.finalized`），再照現在的限流處理：`summary.rateLimited`、回 `rateLimitAbort`；`summary.stoppedAt` 只在這一天沒定案時才設成這一天，否則修復工具的續跑提示會把它誤列成沒抓完 |
| Phase 0（`HistoricalPriceSyncer`） | warning，本輪 log 記「平盤價缺」天數；不進 errors，同 Phase 0 其他單日失敗。之後由下面的摘要計數持續可見 | 同現在的 `RateLimitException` 分支：中止 Phase 0 |
| `tool/backfill.dart` | 不抓平盤價（`withBasePrices: false`、不傳 ledger） | — |

`tool/backfill.dart` 寫的是校準 DB（預設 `tool/calibration.db`）。`tool/` 裡沒有讀 `price_change` 的程式，而且範圍常常超出已經驗證
過的日期，所以三個函式加一個 `withBasePrices` 參數，預設 true，只有它傳 false。

**每輪摘要計數**：數「漲跌因為缺平盤價而是空值」的列，大於 0 時附一行。
- 計數條件：
  - 上市：收盤非空、漲跌空值的列。本設計之後，上市只有缺平盤價時才會這樣：需要平盤價的 `STOCK_DAY_ALL` 列、MI_INDEX 的 X、
    STOCK_DAY 的 `X0.00`。上市的 FinMind 只有 `tool/backfill.dart` 寫校準 DB 會走到。
  - 例外：市場依目前的主檔判斷，所以轉上市股票在轉市場前的上櫃列也算在上市（例：8908 的 3 列除權息文字標記）。這幾列由上櫃的修復
    處理（第 4 節）；轉市場前漲跌空值、非除權息的列（主要是掛牌前的 FinMind 列）修不掉，見已知限制。
  - 上櫃：配發表有這檔這天、收盤非空、漲跌空值的列。上櫃只有 FinMind 價格的股票（興櫃等）本來就沒有漲跌，所以只數除權息列。
- 顯示：列數（上市、上櫃分開），以及最早、最近的日子。
- 它涵蓋所有不會被自動重抓的缺口：
  - Phase 0 寫的、在追蹤起始日之前的日子：步驟 5.5 不會重抓，滑出窗口的 warning 也不管；
  - 抓到了但清單不全的上市列；
  - 滑出 40 天窗的日子。
- 「這天沒有平盤價、但漲跌是對的」（例如那天沒有需要的列）不計入。
- 出現的地方比照「交易日曆待更新」（`result.calendarNotice`）：
  - 通知內文只放一句短句（例：「N 筆漲跌缺平盤價」）；
  - `UpdateResult.summary` 與 update_run 的訊息尾巴放完整的列數與日期。
- 預期狀態：
  - 修復工具跑完之前（副本實測）：
    - 上櫃 1,256 列（現有的除權息空值，683 檔）；
    - 上市 7 列：4 列 `X0.00`（1301、5236、6505、8039），3 列是 8908 轉上市前的上櫃列。

    上市存成 0 的 2,228 列不是空值、不會被數到，由修復工具處理。跑完應該是 0。
  - 新裝機在 Phase 0 收斂前（約 17 輪），逐檔先寫的除權息列也會被數到，屬於預期；Phase 0 補寫時會帶平盤價，計數會自己降回來。
- 查詢耗時：審查者在副本上用 sqlite3 CLI 量這兩個條件，上市約 0.19 秒、上櫃約 0.05 秒。實作時要在 App 的 isolate 裡再量一次。

**逐檔寫入**（上市 STOCK_DAY 月資料、上櫃 FinMind、`tool/backfill.dart` 的 FinMind）不抓平盤價，靠第 2 節保留。

**請求量與間隔**：
- 上市：每次多 1 個（約 136 KB）。每日路徑在交易日每輪一次；步驟 5.5 與 Phase 0 每補一天一次。價格回空（休市日）時不抓。
- 上櫃：只有當天有除權息列時才多 1 個（約 1 KB）。
- 平盤價請求前先等 `ApiConfig.basePriceCallDelayMs`（新常數，1 秒）。這是保守值，同 `finalityRefetchCallDelayMs`；已知 0.5 秒間隔
  連打約 50 次會被證交所擋。
- Phase 0 每輪上限仍以（日, 市場）計 30 個（`historicalMarketDayMaxCallsPerRun`），但上市的每一天變成 2 個請求，常數註解要跟著改。
  新裝機每輪打上市的請求約從 15 個變 30 個（推論，未實測）。

### 4. 既有資料：修復工具

新增 `tool/backfill_base_prices.dart`（純 Dart，跟其他修復工具一樣用 `tool_db.dart` 開 DB）。DAO 新增 `applyBasePrices`：
- 只更新已存在的列：清單上的列寫入 `base_price`，並依第 2 節第 0、1 條重算 `price_change`；
- 同一天、同一市場收盤是空值的列，不論在不在清單上，漲跌都改成空值（第 0 條）；
- 一天（上市）或一個月（上櫃）一個 transaction。

- **上市**：挑價格表裡有上市列、但有平盤價的列不到 `ApiConfig.basePriceBackfillDoneRatio`（50%）的日子，逐日抓 TWT84U →
  `applyBasePrices`。這個條件同時是「做過沒」的判斷，可中斷重跑。不用「有任何一列」（Task 10 審查）：上櫃那一輪會把平盤價寫進
  主檔已轉上市的轉市場列（8908 型），一列就讓那天被當成做過、永遠漏修；比例判錯的方向是「每次都重抓同一天」，看得見。抽測的 5 天（2025-06-10、06-11、06-12、2026-09-16、10-27）都查得到，推論每天都有。
- **上櫃**：對價格表有上櫃列的每個月抓 exDailyQ（整月一次），套用到（代號, 除權息日）已存在的列。上櫃的列沒辦法從資料判斷做過沒
  （沒有平盤價的列多數本來就不是除權息），所以每次全部跑，17 次。
  - 套用時**不依目前主檔的市場過濾**：轉上市股票轉市場前的列（例：8908 的 3 列），主檔現在是上市，但資料是上櫃的，要靠這裡修。
- **請求**：上市 336 天、上櫃 17 個月，間隔 `ApiConfig.repairToolCallDelayMs`（3 秒）。
- **範圍**：只改兩欄，不重抓整天，不動 ledger 與其他欄。第一版被審查挑的「重抓整天的副作用」因此不存在。
- **執行**：先在副本跑、比對（見「驗證」第 9 點），使用者同意後再對 live DB 跑，流程同 Task 15。
- **部署順序**：
  1. 提交後，post-commit 會重編 CLI；從日誌的 `[build=<sha>]` 確認已經換新。
  2. GUI 重編並重開。
  3. 這兩步都完成，才跑修復工具。

  原因：舊程式的 insert-or-replace 會把 `base_price` 清成空值，舊解析器也會把 X 存成 0 並記定案。過渡期內，舊程式整天重寫的日子會
  變回「沒有平盤價」，修復工具挑得到；舊程式逐檔寫的列，平盤價會被清掉，但漲跌是空值（`X0.00`、FinMind），不是 0。
- **不做成每輪自動步驟**：
  - 存成 0 的只有這台的既有資料。新裝機的歷史由 Phase 0（窗口 400 個日曆天，`RuleParams.historyRequiredDays`）經第 3 節的
    函式寫入，自帶平盤價；逐檔補價就算先寫，之後的整市場寫入也會把平盤價補上。
  - 自動步驟要多一套進度紀錄、退避與步驟排序，換來的只是不用手動跑一次工具。
  - 若有其他裝置的 DB 也需要修，再改成自動步驟。
- 之後若有日子因平盤價抓不到而留下空值，又在步驟 5.5 管不到的範圍（追蹤起始日之前，或已滑出 40 天窗），也用這支工具補。

## 熱力圖需求的對照

熱力圖 spec 第 1 節的兩條需求：
1. **語意**：第 2 節第 1 條（有平盤價就是收盤 − 平盤價）；沒成交是空值（第 0 條）；平盤價不明時，第 3 節把「需要平盤價的列」
   改成空值。
2. **除權息日的不變式**：
   - 寫入當下：平盤價與價格在同一個 transaction（第 3 節）；抓不到時存空值，不是 0。第一次寫入走 insert 分支，同樣套規則（第 2 節）。
   - 覆寫：第 2 節保留平盤價並用新收盤重算，例如 21:30 重寫、逐檔補價。
   - 修復工具：`applyBasePrices` 直接寫正確值。
   - 例外只有兩段時間，都有對策：
     - 部署過渡期：舊程式還在跑時照舊行為，所以要照第 4 節的部署順序；
     - 修復工具跑之前的既有資料：照第 4 節執行。

上市減資、面額變更恢復買賣日與上市新股首日，熱力圖 spec 原本列為「沒有已知來源」的已知限制，本版用 TWT84U 一併修正。熱力圖 spec
引用除權息修正現況的段落（現況、不退回前收盤、需求後的排除句、盤中 `y` 待驗證、已知限制、驗證第 0 項）待本設計審查定案後一次同步。

第一版審查後、熱力圖 spec 第四輪審查者列的「重寫的負擔」五點：
1. **15:30 寫入當下就要知道誰除權息** → 第 3 節同一次抓平盤價（上市每天全部；上櫃看文字標記）。
2. **每條寫入路徑同一個 transaction 重算** → 第 2 節唯一入口的 upsert；呼叫點已照第「現況」核對。審查者推論的「上櫃新股掛牌當晚
   FinMind 補價把首日漲跌蓋成空值」由第 2 節第 3 條處理（收盤沒變就保留）。
3. **平盤價要存下來、要寫明取捨** → 第 1 節。
4. **定案重抓的 X 不能記 0；逐檔回補的空值行為** → 第 3 節 X 改空值；逐檔見第 2 節第 2、3 條。
5. **每條路徑的覆寫測試與結構測試** → 「驗證」第 4、5 點。

## 邊界情況

| 情況 | 處理 |
|:--|:--|
| 沒成交（收盤空），含除權息日 | 漲跌空值，平盤價照存（第 2 節第 0 條） |
| 只有現金增資的除權 | 平盤價＝前收盤（6225 例），照公式算 |
| 前一天沒成交 | 平盤價隨揭示價移動，照存（00625K 例）。當天有成交時可能標 X（9/16 的 3432、5906） |
| 平盤價清單上沒有這檔 | 漲跌是非 0 數字的列照用來源值。需要平盤價的列算進 N，照第 3 節的狀態表：抓到了就回報定案＋warning，除非是那兩個例外（上櫃一列都對不上、上市 `STOCK_DAY_ALL`）。8908 轉市場前的列不在上市的寫入路徑上，只會被修復工具碰到 |
| 上櫃新股首日 | 每日行情本來就是數字，照用；基準沒核對（已知限制） |
| 收盤被更正（定案重抓補上鉅額交易等） | 用新收盤與保留的平盤價重算 |
| FinMind 收盤與交易所不同、又沒有平盤價 | 漲跌存空值（第 2 節第 3 條） |
| 颱風停市（例：2026-10-23） | 不用「次日參考價」，不受影響；每天的平盤價以當天的公告為準 |
| 平盤價端點長期失效（例：換格式，`STOCK_DAY_ALL` 2026-06 改 CSV 是前例） | 抓取結果 `failed`：有需要平盤價的列的日子，每日路徑與步驟 5.5 每輪都進 errors（PARTIAL），不記定案；步驟 5.5 每輪重抓到上限，40 天後記 warning；摘要計數持續增加。這是端點壞了，要修程式，所以進 errors |
| 某天的平盤價一直抓不到（端點其他日子正常） | 同上，40 天後滑出窗口，只剩摘要計數。修復工具用同一個端點，一樣抓不到；要等來源恢復，或接受那幾列是空值 |
| 抓到了但清單不全 | 回報定案、warning；上市由摘要計數持續可見，上櫃只有寫入當下的 warning（第 3 節）；不會讓 5.5 反覆重抓。兩個例外照第 3 節 |
| 浮點誤差 | 第 2 節第 1 條四捨五入到小數 2 位；收盤等於平盤價時差為 0 |
| 修復工具中斷 | 上市以「那天有平盤價的列不到門檻」接續（每天一個 transaction，中斷的那天整天回退）；上櫃重跑全部 17 個月 |

## 已知限制

- **大盤家數只排除配發表上的除權息**：不在配發表的不比價列仍照漲跌計入，官方則列為無比價。包括：
  - 減資恢復買賣、新股首日（2026-10-07 量 2025-06 以來 39 筆）；
  - 部分前一天沒成交、當天標 X 的列：9/16 的 3432、5906，修正後是 −0.1、+0.5，官方列為無比價。

  另外，15:30 那輪在步驟 6.6 之前，除權息股也照漲跌計入。要跟官方完全一致，得另存「無比價」標記。每天都會抓的 TWT84U 可能推得出來：
  9/16 有成交的上市列，標 X 的 36 列除了只有現金增資的 6830，平盤價都不等於前收或前收為 0；沒標 X 的有成交列都等於。但證據只有
  一天，列為延後。
- **上櫃新股首日**：沒核對過是不是相對承銷價。
- **轉上市股票轉市場前的空值列**：主要是上櫃新股掛牌前（興櫃期）由 FinMind 寫入的列（漲跌空值），上櫃期間被 FinMind 覆寫成不同收盤
  而清成空值的列也算。這種股票日後轉上市、主檔改成 TWSE 後，這些列會算進上市的缺平盤價計數，而且修復工具修不掉（TWT84U 那些日子
